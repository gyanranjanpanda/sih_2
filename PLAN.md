# PLAN

## What the brief asks for, in my own words

Build a digital twin of a cyclic steam stimulation (CSS) well at Baghewala that couples three
things in one loop: the thermal reservoir around the well, the wellbore and rod string, and the
surface pumping unit with its drive. Put forecasting, diagnostics and two optimizers on top of
it: one that designs the next CSS cycle, one that sets the pump right now. The two must be
genuinely coupled, so the CSS design is constrained by what the pump can survive and the pump
setting is informed by how fast the reservoir is predicted to cool. Data is synthetic and must
be labelled as such, generated by a higher-fidelity simulator that the twin never sees, so that
results are not the twin marking its own homework. Everything must be tested, reproducible,
documented, honest about uncertainty, and runnable from a fresh clone with one command.

## Architecture

```
frontend/            React + TypeScript + Vite dashboard, eight pages
backend/app/
  core/              units, config, errors, logging, numerics, steam tables
  twin/              reduced-order model: fluid, reservoir, wellbore, surface, coupled
    srp/             kinematics (crank and hydraulic), wave, cards, floating, stress, power, pump
  simulate/truth/    higher-fidelity hidden simulator, sealed parameters, sensor model
  ingestion/         CSV adapters, schema and unit validators, quality rules
  ml/                forecast, thermal residual, card classifier, failure risk, anomaly, registry
  optimize/          CSS NSGA-II, pump MPC, CP-SAT fleet scheduler, controller, guard
  api/               FastAPI, /api/v1, WebSocket replay
config/              field.yaml, wells/*.yaml, optimizer.yaml, truth_priors.yaml
scripts/             generate_data, train_models, run_scenario, calibrate, smoke_api
docs/                PHYSICS, ASSUMPTIONS, DATA_SCHEMA, VALIDATION, SOURCES, DEMO_SCRIPT, ...
```

Hard boundary: `app.twin` must never import `app.simulate`. A test enforces it.

M9 dashboard, M10 documentation and submission pack.

## Top five technical risks

1. **Inverse crime.** If the twin is fitted to data the twin made, everything looks perfect and
   means nothing. Mitigation: a separate axisymmetric finite-volume truth simulator with its own
   discretisation, its own wellbore solver, its own rod grid, layered heterogeneity and a sealed
   parameter file, plus an import-boundary test.
2. **Rod dynamics stability.** An explicit wave solver on a tapered string with a switching pump
   boundary is easy to get wrong. Mitigation: Courant condition enforced with a clear error, a
   finite valve transfer distance taken from fluid compressibility rather than a numerical fudge,
   a hysteresis valve state machine on a filtered velocity, and validation against the exact
   damped analytic solution and against the independent Gibbs frequency-domain inverse.
3. **Optimizer cheating.** An optimizer that wins by violating a constraint the baseline
   respected. Mitigation: constraint status is reported for baseline and optimized runs, and the
   scenario script fails if the optimized case violates anything.
4. **Parameter uncertainty.** Almost every Baghewala number is unknown. Mitigation: every value
   carries provenance in config, a robust mode ranks candidates on a conservative percentile
   across a parameter ensemble, and the assimilation layer corrects the twin from measurements.
5. **Scope.** Ten milestones is a lot. Mitigation: physics first, the priority order in the
   brief if time runs short, and never cutting the truth-versus-twin validation.

## Assumptions I changed from the brief, with reasons

1. **Permeability default raised from a first guess to 1500 mD and drainage radius set to 75 m.**
   With 500 mD and a 150 m drainage radius the composite inflow model gives well under 1 m3/day
   for a stimulated well, which cannot be reconciled with a field producing above 1100 barrels
   per day from several tens of wells. Both values were unknown anyway and are marked assumed.
2. **The inflow uses the transient radius of investigation, not the full drainage radius.** A CSS
   well is reopened after every soak, so the flow is transient for much of the cycle. Holding the
   outer radius at the drainage radius from day one overstates the cold-oil resistance and loses
   the characteristic CSS shape of a peak after the soak followed by a decline.
3. **The emulsion viscosity uplift is applied in the wellbore and pump, not in the reservoir.**
   In-situ flow is two-phase oil and water under their own relative permeabilities; the
   water-in-oil dispersion is created by shear in the pump and tubing.
4. **The wave solver uses a node-wise drag linearisation instead of a single Gibbs damping
   factor** when a viscosity profile is available. The drag on the cold top of the string is one
   to two orders of magnitude larger than at the hot pump and a scalar cannot represent that.
   This also removes the double counting between Gibbs damping and the explicit drag term, and
   it is what makes rod float visible in the surface card rather than only in a side calculation.
5. **Conventional unit kinematics use the API Spec 11E four-bar linkage, not an in-line slider
   crank.** An in-line slider crank is exactly symmetric in speed, which would erase the
   upstroke-downstroke asymmetry that matters for rod float.

## Status

  logging, numerics guards, steam tables, Makefile with `make verify`, pinned dependencies.
- M2 complete: ASTM D341 fluid model, Marx-Langenheim injection, Boberg-Lantz style soak and
